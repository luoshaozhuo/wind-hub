## 3. 新增 P1：另一请求占据更高 epoch 后，旧请求仍能解除

### R4-01-P1：续期分支未检查设备最新 epoch 是否超过原裁决

- 级别：**P1（持久 epoch 仲裁与恢复裁决一致性，可实际错误解除 BLOCKED）**
- 状态：**OPEN**
- 位置：`src/commander/infrastructure/event_repository.py:489-506`
- 设计依据：Commander v1_43 §13.1.2，`docs/design/Commander_软件设计_v1_43.md:2719`
- 回归测试：SQLite 组件层与真实 RPC 集成层各一项，均稳定失败

设计要求“允许在最新设备 epoch 未超过该原始裁决的前提下重复确认并解除”，并明确“另一决策已提交更高 epoch，必须拒绝旧请求”。

当前 `commit_recovery` 只判断新证明的 `fencing_epoch` 是否小于设备最大 epoch，随后在 `previous is not None` 分支返回原 decision。它没有判断设备最大 epoch 是否已经大于原裁决 epoch。

确定性复现：

1. `req-old` 提交 epoch=1；
2. `req-new` 提交 epoch=2，设备最新持久 epoch 已超过 `req-old` 原裁决；
3. 旧请求 `req-old` 以相同请求身份、证据和 token，但 epoch=3 续期；
4. 当前实现未拒绝，并返回旧 decision。

真实 RPC 测试进一步构造两个 COMMIT 后第二次核验均 revoked 的请求，二者保持 BLOCKED 且持久 epoch 严格递增。清除 revoked 后用旧请求重试，预期 `INVALID_ARGUMENT`，实际 RPC 未报错并解除 BLOCKED。

最终专项失败原文要点：

```text
test_newer_decision_blocks_old_request_even_with_renewed_epoch
E   Failed: DID NOT RAISE <class 'ValueError'>

test_superseded_request_cannot_release_with_renewed_epoch
E   Failed: DID NOT RAISE <class 'grpc.aio._call.AioRpcError'>
```

这不是仅有 fail-closed 可用性问题：旧请求在控制权代次已被后续裁决超越后取得了新的解除依据，因此本轮不能将 R4-01 判为 CLOSED。修复方向涉及 SQLite 持久仲裁事务，由生产实现方按 v1_43 修改，验收方未自行改代码或降低安全断言。
