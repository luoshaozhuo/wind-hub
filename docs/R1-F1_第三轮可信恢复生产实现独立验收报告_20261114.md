### 3.1 已排除的误报

`pending_events(limit=100)` 为恢复 Outbox 保留槽位，真实 250 条普通事件积压时同批仍取出恢复事件；metrics 合并普通与恢复 pending/oldest。不存在独立审查所假设的“恢复 Outbox 永久饥饿”。

### 3.2 `recovery_blocks`、清理、迁移和重复重启

真实 SQLite 证明：UNKNOWN 恢复生成设备阻断；历史事件发布并清理后阻断仍保留；成功裁决只授权当前进程内存解除，不删除安全屏障；第三次打开数据库仍阻断。删除旧库 `recovery_blocks` 模拟迁移时，启动会在历史清理前从 UNKNOWN 事件重建阻断。

## 5. S4 真实 SQLite 与真实 JetStream

### 5.1 SQLite

专项 `tests/commander/component/test_recovery_repository.py`：**5 passed / 1 failed**。唯一失败为旧 epoch 幂等重放，属于生产 P1。

已通过：UNKNOWN 重启、保留期清理、成功裁决后的再次重启、旧库升级重建、token 唯一、普通 epoch 单调、Outbox 预留槽位、251 条 pending 指标、无原始证据、事务故障 ROLLBACK 后仓储仍可操作。

真实独立进程崩溃测试不是进程内重建替身：子进程在 `commit_recovery` 返回后发送 committed 标记并 `os._exit(73)`；父进程确认退出码，再用 SQLite online backup 包含 WAL 重启。旧进程没有执行本地 release，重启不会根据历史 decision 自动 READY。

### 5.2 JetStream

真实 Docker JetStream 已证明：

- `RECOVERY_FENCE_COMMITTED` 由真实 PubAck 确认，decision_id/event_id 稳定；
- 恢复事件包含证据摘要、token、epoch、旧/新实例，不包含原始 attestation；
- 恢复审计排空、Watchdog 提升 READY、新命令审计落盘后，完整 7 事件顺序为旧 ACCEPTED/COMPLETED、RECOVERY_FENCE_COMMITTED、新 ACCEPTED/CONNECTING/EXECUTING/COMPLETED，事件 ID 无重复；
- `docker stop` 期间恢复裁决仍持久化在 SQLite Outbox，不伪装成已发布；
- `docker start` 后重投排空，流内仅一条恢复裁决，无重复审计；
- 旧 UNKNOWN 不变、现场写零重发。

**真实 JetStream 已接收消息但 PubAck 在网络上丢失的精确注入：NOT_RUN。** 本轮未用普通重复发布或 Mock ACK 冒充 ACK 丢失。物理磁盘满、存储介质损坏亦为 NOT_RUN；SQLite 触发器只证明事务失败回滚路径。

暂时性 JetStream 中断依赖已提交 Outbox 重投，和 AuditDelivery worker 已停止不是同一状态。后者表示审计机制不可用，当前恢复入口却只检查 `journal.operational`，因此判 P1。

## 8. 设计一致性边界

Commander v1_41 §2676 要求“落盘成功且再次确认隔离证据有效后才解除阻断”，§2709 又只写“事务成功且证据未过期后”解除。实现只有后者。按本轮明确安全不变量及更强安全条款，R1-F1-R3-03 必须关闭后才能通过。

设计同时要求 JetStream 异步 Outbox 重试，因此不能把每次暂时发布失败都等同为禁止持久恢复；但 §2676/§2678 的“提交/核验/审计任何一步失败不得解除”和“审计不可用保持 BLOCKED”至少要求停止的审计 worker 不得被忽略。当前实现没有此门禁。
