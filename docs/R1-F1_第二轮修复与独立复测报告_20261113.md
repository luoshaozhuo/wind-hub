## 5. S2：F1-GAP-02 设计裁定材料（§4.3）

### 5.1 当前设计依据及缺失内容

- UR-15.3/15.4：旧进程 I/O 与设备控制权未确认安全结束/隔离前不得新建冲突写入；
  允许"隔离**或维持阻塞**"（维持阻塞是合规安全态，当前实现即此态）。
- SR-03/SR-04、RR-05、图 6-9、§13.1：解除 BLOCKED 需要"可信安全结束或隔离证据"，
  图 6-9 中证据来源是**本进程协议适配器**（P-->>S）。
- **缺失**：进程重启后旧 I/O 已不可能在本进程被观测，设计未定义此情形下的
  证据来源、证据结构、校验方式、可执行解除的权限角色（viewer/ops/deployer）、
  审计事件格式与解除流程；Common 9 + Commander 7 RPC 已冻结，**无任何 isolate/unblock 入口**；
  FR-09 Reload 只规定配置切换的隔离等待，不是恢复解除通道。

### 5.2 现有代码与接口约束

- `isolate_device()` 唯一的合规证据源 = 本进程原生任务收敛 + `Session.close()` 物理关闭；
  恢复后二者皆无（本轮起无证据时 fail-closed）。
- 任务书 §4.2 排除全部进程内自证信号；SQLite flock/单 Writer 只证明同机存储互斥，
  不证明现场控制权（SR-04）；不得新增 RPC、不得 force=True、不得未验证布尔确认。

### 5.3 推荐的最小安全恢复方案（供裁定，未实施）

方案 A（推荐）：设计新增"恢复设备解除隔离"运维流程——
ops/deployer 权限经**新 RPC 或 Contracts 扩展**提交解除请求；Commander 校验
(a) 部署/进程管理层出具的旧实例已终止且旧 epoch 不再重启的独占控制权证据，
(b) 现场只读状态核对（辅助证据，不单独成立）；记录结构化审计
（operator、device_id、证据引用、配置 revision、时间）；解除后复用既有
Watchdog DEGRADED→READY。需修改设计：§9/Contracts RPC 清单、§13.1 权限与审计、
§14.4/UR-15 恢复流程；需修改生产：`contracts/*.proto`、`commander/infrastructure/grpc/server.py`、
`service_lifecycle.py`、`queued_executor.py`、CLI 对应命令与测试。

方案 B（不新增 RPC 的备选）：设计明确规定恢复设备只能经"设备级配置删除→重新添加（Reload）"
在部署层独占保证下重建控制会话，并把该流程的合法性、证据与审计写入 §11.5/§14.4。
仍需正式设计修订，不能由实现层自行认定合法。

### 5.4 为什么无法在现有契约下安全实现

合规证据必须来自进程外（进程管理/运维授权/现场协议证据），而现有冻结 RPC 没有任何
携带该证据的入口；进程内可获得的全部信号均被 UR-15.4、图 6-9 与任务书 §4.2 明确排除。
任何"实现层自定义证据"都等同于新增契约，故按 §4.3 停止生产开发。
