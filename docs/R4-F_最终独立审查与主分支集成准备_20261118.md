## 3. F2：设计及接口一致性

### 3.1 已一致或已修复

- CommonService 仍是六进程统一契约；本轮未修改 Proto。
- Gateway 租约仍由认证 principal 与业务 owner_id 双重约束，新增 owner 输入限制不改变 RPC 字段。
- Realtime/Reliable 数据面职责未混淆；诊断证据是只读观测，不进入消息线协议。
- Collector 仍使用双 Collector 身份和双 Subject；部署模式统一为 `collector_realtime`、`collector_reliable`。
- CLI 诊断现在使用正式 Collector/Sink stage，不再发送服务端不识别的小写或旧枚举。

### 3.2 契约或设计缺口

1. **systemd 设计与实现不一致**：R4-F 未发现可兼容旧 systemd 配置的加载路径。该问题影响已有 systemd 部署升级，是主分支集成阻断。
2. **Reliable 诊断能力未完整定义**：当前正向 pipeline 只能严格证明 Realtime；若设计要求双通道诊断 PASS，必须补齐 Reliable 证据契约。
3. **历史配置治理证据不完整**：I-08 中 Collector stale Apply 有真实证据，但 Gateway/DG/Sink/Commander 的正常 Push/Apply 主要来自历史专项，R4-F 未重跑原始 pytest。
4. **Proto 未变化**：`generate_rpc.py --check` 通过；本轮没有引入需要评审的字段号、oneof 或兼容性风险。
