### 5.1 生产 STMT2 阶段耗时与批量

| Prepare | Columns | Bind | Execute | 行/execute | 设备绑定/execute |
|---:|---:|---:|---:|---:|---:|
| 0.0015ms | **29.628ms** | 9.253ms | 11.189ms | **65.978** | 63.440 |

这些是按 256-write 窗口、按调用数加权的生产均值，不是原生代理测试。现有生产指标没有逐次 columns/bind/execute 样本，故不能伪造生产阶段 P95/P99；只有上节 Kafka ACK 与下节 Sink gRPC/写窗口 P95/P99 为实测量。逐条 queue wait 也没有生产计时，报告只给真实 buffer/lag，不用均值反推排队时间。

### 5.2 为什么每次 execute 只有约 72 行

72 不是 TDengine 或配置的固定上限：

1. 当前配置允许 `batch_max_rows=1000`、`batch_max_bytes=8MiB`、`max_poll_records=500`，500 点行远未触及 8MiB 字节预算。
2. 容量 topic 明确为 **3 partitions**；Kafka dispatcher 按 partition 调用 `WideIngestionService.process()`，每个 partition 独立解析、合批、flush 和提交连续 offset，不能把三个 partition 合成一次 execute。
3. `process()` 只对本次 partition 输入按 farm/schema 分组；本轮只有一个 schema，所以每次 partition flush 基本就是一次 STMT2 execute。全局 500-row poll 被三个 partition 和立即可取数据拆分后，不会自然形成每 partition 1000 行。
4. 因而 72 是“poll 可用数据 + 三分区拆分 + 单 partition flush”形成的实测水位，不是硬编码。上一轮 72.45、本轮 65.98 都符合该路径。代码定位见 `batch_origin_code_refs.log`。

## 7. 缺陷分类与下一步

### 本轮发现

- **TEST_DEFECT（已修）**：容量 monitor 在 channel close 后取样及关闭顺序导致 CancelledError。相关初次失败目录完整保留，只有 `*_metered_final` 和 `storage_100_metered_valid` 用于计量结论。
- **TEST_DEFECT（已修）**：performance Fixture 配置版本路径漂移，修复后 7/7。
- **FORMAT（已修）**：交接 HEAD 的 wide_stmt2 格式漂移。
- **PRODUCTION CAPACITY（未关闭）**：Storage 30/100 端到端临界失败、300 台持续积压；Sink 60/600s 持续容量失败。它们是本轮重新实证的生产容量缺口，不伪造“新功能缺陷”。

### 最有证据支持的优化方向

1. **Storage 优先提高每 partition 的有效批量并覆盖解码/调度耗时。** 当前每次 execute 约 66 行，columns+bind+execute 已约 50ms；继续缓存工厂查找收益很小。应在保持 partition FIFO、UNKNOWN fencing 和连续 offset 提交的前提下，测量并优化 poll→decode→writer queue→flush，评估有界地积累更大 per-partition batch，而不是跨 partition 破坏确认语义或盲目调参。
2. **补充低开销生产 queue/decode 计时后再做结构整改。** 当前只有 STMT2 阶段均值和 buffer/lag，不能准确分配 JSON 解析、schema resolve、重复 row bind、writer permit 的耗时；先取得这些真实分布，避免把 50ms 数据库阶段误当成全部链路。
3. **Sink 优先处理 native quota 与 Kafka submit/confirm。** encode 已约 0.44ms，600s 持续积压证明需要生产链路整改；不建议再扩大短矩阵或增加发布编码进程。

结构性生产修改交 ChatGPT；本轮只修改 Fixture 和格式。

## 8. 最终结论

工厂缓存优化可保留，但不能关闭容量阻断。300 台 Storage 的发布器、TDengine 数据完整性和最终追平均通过，持续 lag 仍快速增长；Sink 600s 虽较上一轮 205.75 提升至 226.80 批/s，仍显著低于 300 目标。总体保持 **BLOCKED**，不得进入生产就绪裁决。
