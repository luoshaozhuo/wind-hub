`tests/sink_service/unit/test_kafka_encoded_batch.py`、`test_reliable_sample_evidence.py`、`component/test_metrics.py` 全绿，覆盖：

- 同 Stripe 串行、异 Stripe 可并行。
- Kafka stage 按 owning Delivery 归属，并经 Runtime metrics 输出；Service 聚合和 Delivery scope 均有测试。
- R14 最终 JSON 与逐秒 JSONL 均记录 `kafka_timed_writes_total` 和 lock/metadata/submit/confirm 累计秒数。

真实 R14 逐秒样本中，四段计时与 timed writes 均非负、单调不减。最终两工况的 `kafka_timed_writes_total` 增量与 `reliable_write_operations_total` 增量完全一致：120 为 5877/5877，300 为 5504/5504。

### 3.2 明确的计时覆盖边界

当前 `kafka_stage_seconds` 只在 `write_encoded_batch()` 返回带计时的 `BatchOutcome` 时累计。以下路径不完整：

- 未连接、空 payload、Metadata/partition 解析失败的提前 return 不带 `kafka_stage_seconds`。
- 取消及少数未形成正常 `BatchOutcome` 的异常路径不累计。
- `_QuotaWriter` 在调用 KafkaOutput 之前等待 global/Sink quota 的时间不属于四段。
- Reliable heartbeat 包装与 KafkaOutput 外部等待也不属于四段。

因此四段之和不能解释为所有情况下的完整 `reliable_write`，缺失时间也不能计为零。本轮零失败容量工况中 timed write 次数完整，但正常路径仍有显著未归属等待，见下节。

## 5. Kafka 瓶颈分项回答

### A. 锁竞争

Stripe lock 平均只有 0.002–0.003 ms，累计 12–16 ms。**没有证据支持 30 设备发生严重 Hash Stripe 冲突，也没有证据表明设备锁是瓶颈。** 但这不排除 KafkaOutput 之外的 shared/global quota 串行化。

### B. Metadata

初始建缓存累计约 0.49–0.70s，后续差分接近零，Partition Cache 有效。Metadata 不是持续期瓶颈。

### C. Producer 提交

`send_batch()` 提交平均 30.70–33.37 ms，是 KafkaOutput 内部四段中最大项，显著高于 confirm。它可能包含 Producer 内部排队、BatchBuilder 调度或客户端事件环等待；现有指标不能继续拆分。

两工况 topic 都只有 **1 个 partition**，所有确认值都在 partition 0。因此不存在“集中至少数分区”的猜测问题：当前就是单分区，Producer/Broker 无法利用 topic 分区并行。是否应增加生产 topic 分区数属于架构与消费归属设计，需 ChatGPT 决定，本轮未擅自修改。

### D. Kafka 确认

应用等待 Confirmation Future 平均 7.67–8.33 ms，小于 submit。**该值不是 Broker 纯处理时间**，仍可能包含 Producer 内部队列与客户端调度。现有指标无法分离 Producer 排队和 Broker 真正处理时间。

### 瓶颈排序

1. **KafkaOutput 之外、`reliable_write` 之内的未归属等待：248–270 ms/写**；最可能为 `_QuotaWriter` global/per-Sink quota 获取及共享物理输出串行化，需直接计时证实。
2. **Producer submit：30.7–33.4 ms/写**。
3. Confirmation Future：7.7–8.3 ms/写。
4. source fetch/ACK、encode、Stripe lock、稳态 Metadata：相对较小。

单 Kafka partition 是已证实的拓扑限制，但其对当前回退的独立贡献尚未通过分区数对照实验量化。

## 6. C5 / C6 第一轮 / 第二轮对比

| 工况 | C5 | C6 第一轮 | C6 第二轮首次 | C6 第二轮最终 |
|---|---:|---:|---:|---:|
| 120 目标 | 116.62 | 97.90 | **117.73（PASS）** | **102.11（FAIL）** |
| 300 目标 | 122.38 | 97.72 | 119.80 | 93.85 |

结论：

- 约 98–120 批/s 的平台区间可复现，但具体回退数值不稳定。相同第二轮代码下，120 工况一次达到 117.73、一次只有 102.11，**不能仅凭吞吐值断言某个提交造成回退**。
- RSS 约 254 MiB，基本一致；topic 分区数在两组最终工况均为 1。历史 C5/C6 第一轮未保存同口径分区证据，无法严格证明三轮拓扑完全相同。
- 测试机存在多套遗留 R5 容器，未做 CPU/IO 隔离；Docker/Broker 资源差异是明确的环境风险，但本轮没有足够受控数据将其定为根因。
- 300 工况发布端只有 248.57，说明发布端也未达到目标；但 Sink 确认端约 94 且积压持续增加，是独立的更低上限。
- 共享 Producer/物理 Sink 与事件循环瓶颈均有迹象，但当前最明确的证据是 quota/KafkaOutput 边界存在大量未计时等待，而不是单独 confirm 或设备锁。

### 已证实

- Stripe 锁和稳态 Metadata 不是主要耗时。
- submit 大于 confirm。
- topic 为单 partition。
- `reliable_write` 有大量时间不在 Kafka 四段内。

### 证据支持但未完全证实

- shared/global quota 或共享物理 Sink 串行化是主要等待位置。
- Producer submit 内部排队是 KafkaOutput 内部首要优化点。

### 尚需实验

- 增加 `_QuotaWriter` global/per-Sink acquire 等待指标，分解未归属时间。
- 在固定 R5 资源、相同 CPU/IO 条件下做分区数与 quota 的单变量对照；不得直接扩大生产并发。
- 对 Producer 内部排队与 Broker 纯处理增加客户端/Broker 双侧证据。

## 10. 给 ChatGPT 的具体整改建议

1. 在 `_QuotaWriter._start_write()` 分别计量 global quota、per-Sink quota 等待和实际 native operation 时间，并传递到 Delivery/Service scope；这是闭合 248–270 ms 缺口的下一步。
2. 保留当前 Kafka 四段，不要把 confirm 命名为 Broker 处理时间；补充 Producer 内部 submit 排队细分。
3. 在受控 R5 环境做 topic partition 单变量实验，同时审查 Storage 消费键和分区归属，再决定生产分区数。
4. 为未连接、空 payload、Metadata 失败、提交失败、确认失败和取消定义明确的计时覆盖语义；缺失应显式不可见，不能填零。
5. 容量比较必须记录 R5 容器数量、topic 分区、CPU/IO 隔离与发布端能力，避免把环境波动误判为代码回退。
